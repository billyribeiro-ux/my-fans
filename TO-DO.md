# TO-DO — owner setup and production launch

Prepared October 8, 2026. Service recommendations were checked against official sources on that date; application dependency choices retain the October 7 cutoff. This checklist applies to the implemented **general-content creator platform**.

The latest frontend review and local release results are recorded in the [Svelte audit](docs/svelte-idiomatic-audit.md); [verification](docs/verification.md) retains the earlier backend, infrastructure and operational evidence. Your remaining work is to obtain approved accounts, supply real business information, authorize the deployment, complete acceptance in those accounts, and assign ongoing operations. You can delegate the technical tasks below to your engineer; business approvals, account ownership and spending decisions remain yours. Check items only after the result is recorded.

## 1. Confirm the business before committing to services

- [ ] Confirm the actual legal operator, business address, launch countries, bank account, tax identifiers and authorized account signatories. Use the same real operator information in provider applications and public policies.
- [ ] Confirm that the product will follow the approved general-content rules. **This implementation and provider selection are not an adult-content launch package.** Obtain Stripe's approval specifically for a creator platform offering subscriptions, purchases and content-related tips. Stripe's prohibited sexual-content rules are broader than a prohibition on explicit nudity. Identity verification does not change those restrictions. [Stripe business restrictions](https://stripe.com/legal/restricted-businesses)
- [ ] Approve the implemented USD, monthly-subscription and 20% platform-fee model. Confirm that processing fees, tax, refunds, disputes and payout charges leave acceptable margins. Changing currency, fee calculations or the charge model requires implementation and renewed tests, not just editing policy text.
- [ ] Confirm that US-region data processing is appropriate. The supplied cloud launcher targets `us-east-1`; a different residency requirement needs an architecture/configuration review before deployment.
- [ ] Approve the brand, production domain and rights to production imagery/content. Production must start with a fresh database; do not import the seeded demonstration users, passwords, balances or stock-content fixtures.

- [ ] Download and retain the attested bundle and corresponding source before the configured **14-day GitHub artifact retention** expires. Preserve its checksums and exact image identities.

**Optional automatic ECR publication has a known setup dependency.** The current `deploy/aws/github-release-role.json` constructs a legacy name-only GitHub OIDC subject. New repositories created after July 15, 2026, and later renamed/transferred repositories use immutable owner/repository IDs. Before enabling `publish_ecr=true`, have the engineer update and test the narrow trust template against the repository's actual subject, with the protected `release` environment and exact repository scope. This is a template change, not merely filling in an account ID. Keep automatic publication off until verified; retain the attested-build/operator-publication path above. [GitHub immutable subjects](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims)

## 7. Have the engineer deploy in this order

Authorize the target account and spending before this sequence. Detailed commands and change-set review requirements are in [AWS runtime](docs/aws-runtime.md). Record each completed stage and its evidence.

- [ ] Authenticate the deployment role and run `bootstrap-storage` to enable regional EBS encryption before compute launch.
- [ ] Plan, review and apply **registry**; this initial stage needs only account, region and deployment name. Then complete the production-origin release/publication steps above.
- [ ] Finish `.local/aws-production.json`, the provider secret and the approved policy secret, with registration initially **false**. Run `preflight` against the actual account.
- [ ] Plan, review and apply **foundation**, then **media**, then **runtime**, waiting for each stack to finish. Runtime initially has zero replicas. Preserve private networking, backups and scoped roles.
- [ ] Run `migrate` with the separate owner task and apply the restricted runtime grants. Plan/apply **edge** after runtime/migrations, then run the privacy-maintenance setup.
- [ ] Run `start` and `doctor` on the actual managed hosts. Check database TLS, current scanner signatures, real sandbox enforcement, storage access, workers and all required providers. A successful configuration diagnostic alone does not certify provider acceptance.
- [ ] Confirm the SNS alarm email subscription and exercise actual alert delivery, queue/DLQ visibility and escalation.
- [ ] Open a tightly controlled administrator-enrollment window: securely publish the approved policy with registration **true**, run `reload-policy` against that approved document, and verify the served policy before enrollment.
- [ ] Register your administrator through the UI, receive and use the real verification email, enroll MFA and preserve recovery codes. Run `bootstrap-admin` for that exact verified email. No default production administrator exists.
- [ ] Immediately publish the approved policy with registration **false**, reload both services, and verify false is served. Keep general registration closed while acceptance is completed.

Policy and secret values are loaded when tasks start. Updating a secret alone does not update running services. Use the documented reload/restart procedure and avoid concurrent secret changes. For a closure that cannot tolerate rolling overlap, use the documented pause/update/start/verify maintenance sequence. [Policy changes](docs/aws-runtime.md#updates-and-secret-changes)
