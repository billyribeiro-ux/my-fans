# Provider accounting and operator recovery

Stripe direct charges belong to the connected creator account. The application never converts a sandbox wallet into a Stripe payout. New checkouts require connected accounts with USD as their default settlement currency, matching the supported USD pricing and exact receipt reconciliation; cross-currency settlement is rejected before payment creation. The immutable provider journal records every balance transaction separately from the sandbox double-entry wallet. Each journal transaction exposes three signed postings—gross source, fees, and Stripe balance—whose total is zero in the transaction's currency. Database constraints enforce the arithmetic and reject changing or deleting posted financial identities. Corrections, refunds, dispute movements, and failed payout returns arrive as new provider transactions.

Five durable scans run independently for each connected account: balance transactions, payouts, payout membership, disputes, and payment receipts. Initial history starts at the Unix epoch, so finance recovery does not depend on the Events API's retention window. List requests carry a fixed upper timestamp, overlap the previous completed window, persist the provider cursor, reject a repeating cursor, and process at most 25 records (five disputes) per job. Per-account leases prevent one unavailable creator from blocking another. Pending balance transactions and unresolved disputes receive additional current-object refreshes; payout scans overlap fourteen days because a payout initially reported paid can subsequently fail. A bank statement remains the external evidence of actual bank receipt.

Every paid receipt is independently compared with its current charge, balance transaction, platform application fee, and inclusive Stripe Tax total. The platform application fee is retrieved in platform scope and verified against the connected account and charge, rather than trusting a webhook amount. One-off fees must equal the configured integer 20% fee. Subscription percent fees accept the two adjacent integer representations of exactly 20% (a maximum one-minor-unit rounding difference). Missing or inconsistent provider information leaves the receipt unverified and produces a discrepancy or failed job; no scan manufactures an entitlement or changes a payment amount. Taxes are reported from the provider's completed calculation; this is not evidence that a tax return was filed or remitted.

Automatic payouts with completed reconciliation are matched to their provider-listed balance transaction members, across durable pages, and checked against the sum of member net amounts in the payout currency. Manual payouts remain explicitly unattributed because Stripe does not supply the same transaction attribution for them. Current payout status, expected arrival, original balance transaction and failure return are retained without bank account numbers. Negative balances and processor fees remain provider facts, never simulated local settlements.

The administrator finance screen is available under `/admin`. All finance reads and actions require an active administrator account and recent MFA. Lists use independent 50-record keyset cursors. The scanner summary shows open discrepancies, failed finance jobs, unverified receipts, and next due time. Acknowledging a discrepancy records the actor and a required 5–500 character reason. It does not resolve that discrepancy; a subsequent verified scan must do so. If a resolved discrepancy recurs, its acknowledgment is reset. Financial operator actions are immutable audit records.

An indeterminate checkout remains reserved until its provider session is found. An administrator can attach a session only when its connected account, session identifier, local checkout reference, purchase mode, currency, and amount match. The application then retrieves and synchronizes the current provider status. There is no force-paid action, no assumed failure based on an empty list, and no new charge request from this recovery action. If no session can be identified, the case stays open for Stripe support investigation.

Disputes are retrieved from Stripe at processing time, including current status and response deadline. Evidence is submitted through Stripe's hosted dashboard. New disputes and refunds revoke the affected paid period or purchase. A merchant win does not automatically restore access. An administrator can request restoration with an audit reason only after current charge and all current charge disputes are verified, with a merchant win, zero refunds, and no other adverse dispute. The restored entitlement must be the exact entitlement this financial workflow revoked, with the same revocation timestamp; expired periods, previously non-financial revocations, and disabled users remain ineligible. A subsequent refund or adverse dispute revokes access again. The historical `charge.disputed` flag alone does not undo an explicitly verified restoration.

Refund requests require an audit reason in production; sandbox requests accept an optional reason for backward compatibility. The existing checkout refund action requests the remaining refund on the first paid invoice or one-off charge, including the application fee, with a stable idempotency key. Its `processing` response means a request was made; the interface does not claim completed money movement. Later invoice or partial refund operations can be performed in Stripe's hosted dashboard and are reconciled into the same journal and entitlement lifecycle. Real merchant support decisions, evidence, fee responsibility, and tax liability require the operator's approved policies and provider configuration.

Production accepts only live Stripe keys and sandbox accepts only test keys. The surrounding production startup gate requires the configured external services and operator policy facts. Accounts, webhook registration, approvals, tax registrations and actual provider/bank acceptance are supplied in the target environment; fixture tests do not replace that acceptance.

## Verification

The local fixture suite covers immutable balanced money, idempotent replay, changed provider amounts, unknown charges, full-history cursor recovery, repeating-cursor rejection, automatic payout member totals, explicit manual-payout non-attribution, fee and tax verification, wrong-session recovery rejection, audit immutability, administrator authorization, acknowledgment without financial resolution, merchant-win restoration and subsequent refund revocation. Tests use disposable PostgreSQL databases and real HTTP requests to a local provider fixture using the pinned Stripe API version; no remote charge or payout is created.

## Primary contracts

- [Stripe balance transaction object](https://docs.stripe.com/api/balance_transactions/object) and [reporting categories](https://docs.stripe.com/reports/balance-transaction-types): source identity, fee/net arithmetic, pending versus available funds.
- [Stripe payout object](https://docs.stripe.com/api/payouts/object) and [balance transaction listing](https://docs.stripe.com/api/balance_transactions/list): payout membership is available for supported automatic payouts; a reported paid payout can later fail.
- [Stripe dispute object](https://docs.stripe.com/api/disputes/object): current outcome, response deadline, and withdrawn/reinstated balance transactions.
- [Stripe Connect subscriptions](https://docs.stripe.com/connect/subscriptions): direct-charge ownership and percent application fees on final invoice amounts.
- [Stripe invoice object](https://docs.stripe.com/api/invoices/object) and [Checkout Session object](https://docs.stripe.com/api/checkout/sessions/object): current total tax fields under the pinned API contract.
