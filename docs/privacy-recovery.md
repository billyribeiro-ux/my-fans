# Privacy-safe snapshot recovery

Database snapshots can predate an account's erasure request. Recovery therefore requires a separately exported, KMS-signed privacy journal in addition to the database snapshot and media checkpoint. Source services are drained before export. The journal includes every request's status, hold, captured retention schedule and original dates, plus exact media keys belonging to already erased accounts.

`privacy-export` accepts `PRIVACY_SOURCE_DATABASE_ID`, `PRIVACY_JOURNAL_BUCKET`, `PRIVACY_JOURNAL_KEY`, `PRIVACY_JOURNAL_KMS_KEY_ID`, `S3_EXPECTED_BUCKET_OWNER` and `AWS_REGION`. It checks the source RDS endpoint, owner login, absence of other database clients and original storage binding. Export uses one repeatable-read snapshot and is bounded to100000 requests,100000 media keys and32MiB. It uploads a create-only SSE-KMS object and requires a non-null S3 version. Cloud orchestration signs the exact version/hash/source envelope. Conditional creation and version identifiers follow the [S3 PutObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html).

Rebinding an isolated restore marks `platform_recovery` quarantined in the same transaction as its new storage identity. API and worker startup refuse that state. Storage verification and owner maintenance remain available. The restricted application role cannot clear the gate or modify immutable recovery audit records.

Cloud orchestration verifies the KMS envelope, removes journal-listed erased keys before copying checkpoint objects, then invokes `privacy-replay`. Replay takes the exact `PRIVACY_JOURNAL_BUCKET`, `PRIVACY_JOURNAL_KEY`, `PRIVACY_JOURNAL_VERSION`, `PRIVACY_JOURNAL_SHA256`, `PRIVACY_SOURCE_DATABASE_ID`, `PRIVACY_SOURCE_STORAGE_ID` and `RECOVERY_DATABASE_HOST`, plus region/expected owner. Rust independently verifies object version, bounded body, SHA-256, JSON version, source binding, owner access, sole database connection and exact isolated RDS hostname. It never infers a journal from a latest-object listing.

Replay freezes pending and held accounts, revokes sessions/recovery tokens, prevents content publication and cancels restored media jobs. Already erased accounts are pseudonymized again; personal content is scrubbed in bounded batches, excluded media references are removed, and assets remain rejected. Original request scope and retention dates must match any restored request. Holds are never implicitly released. Financial IDs and money records remain intact for reconciliation and their captured retention workflow.

Each batch commits its effects and cursor together. Interruption leaves the database quarantined; only the same immutable journal resumes that cursor. Missing users that did not yet exist at snapshot time are recorded as processed without inventing accounts. Completion writes an immutable audit with source/target identities, object version/hash and counts before opening the gate. Replaying the same completed journal is idempotent.

The operator must supply a signed journal at least as current as the desired erasure recovery point. The cloud recovery workflow requires an explicit acknowledgment when a deliberately stale checkpoint/journal is chosen. Software cannot reconstruct requests absent from both the database snapshot and the selected journal. This requirement is separate from the provider, legal-hold and backup-retention completion evidence in the ordinary erasure workflow.

Focused tests cover source/key/state rejection, a205-row personal-content scrub, post-snapshot erasure and holds, missing users, session/media denial, preserved paid records, interrupted replay, different-hash refusal, runtime-role denial and immutable/idempotent completion.
