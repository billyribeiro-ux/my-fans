# Provider integration and acceptance

The selected product policy is **general creator content; explicit adult content is prohibited**. The selected adapters are Stripe Connect, Sumsub, private Amazon S3, ClamAV, and authenticated TLS SMTP. Both isolated provider testing and production configuration are implemented. Production requires matching live keys, approved operator policy, private storage, SES feedback and restricted TLS database credentials. Fixture seeding is refused in provider environments; actual provider acceptance requires your approved accounts.

Use [the environment template](../deploy/providers.env.example) in an isolated environment. Supply real account identifiers and secret **file paths** through the deployment's configuration manager. Do not commit secrets or paste them into chat. The template contains placeholders and cannot be used unchanged. `PUBLIC_ORIGIN`, `MAIL_PUBLIC_ORIGIN`, and the frontend's build-time `APP_ORIGIN` must identify the same HTTPS origin. The existing private Compose launcher is for local sandbox staging and does not provision these services or public TLS.

## Stripe Connect

The adapter uses Connect Express **direct charges** in each creator's connected account, hosted Checkout, and hosted onboarding/dashboard links. Stripe manages bank payouts. USD is the supported currency. Monthly subscriptions use a 20% application fee; one-off purchases and tips use the server-calculated fee. Checkout prices are inclusive of tax and enable Stripe Tax. Creator tax settings and registrations must be configured and accepted before provider testing. The connected-account launch country is an operator fact, supplied with `STRIPE_ACCOUNT_COUNTRY`.

For isolated acceptance configure a test Stripe platform; production uses the approved live platform. Configure Connect and a connected-account webhook destination at `/api/webhooks/stripe`, using snapshot API version `2026-09-30.endive`. Mount the mode-matching Stripe key (`sk_test_...` in sandbox; `sk_live_...` in production) and the endpoint's `whsec_...` signing secret. Subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`, `invoice.paid`, `invoice.payment_succeeded`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, and `charge.dispute.funds_withdrawn` for connected accounts. Other signed connected-account events are acknowledged without business effects.

Creators need verified email and a recent MFA session for onboarding/dashboard links. New purchases require the creator's local review approval and provider account charge/payout capabilities. Hosted URL hosts are exact allowlists; returned links are not persisted. A browser return never grants access. Raw webhook signatures require an exact body and a timestamp within five minutes. Event identity/digest and a durable job are committed before acknowledgment; current provider objects are retrieved using the pinned API version. Original webhook PII is not stored.

The adapter verifies payment currency and captured amount, deduplicates charge/invoice receipts, and grants access only for a paid charge or paid subscription invoice. It supports one card payment and one monthly item per invoice; unsupported invoice shapes fail closed. Current subscriptions remain reserved until the provider reports cancellation, rather than expiring locally during a delayed renewal. Refunds and disputes revoke the affected entitlement; a later older observation cannot restore it or reduce the recorded refund. Administrative checkout refunds target the original purchased period; other period-specific refunds and dispute evidence are managed in Stripe. Creator balances come from Stripe. The local double-entry ledger and local payout reservations remain sandbox-only; separate immutable provider observations independently reconcile live charges, fees, taxes, refunds, disputes and payouts.

Reconciliation leases independent jobs per connected account, so one account failure does not block other creators. It reads events in bounded durable pages, with a ten-minute overlap and five-minute poll interval. It resumes the same bounded event window and fails visibly if the last checkpoint exceeds the provider's event-retention window. Failed jobs are visible to administrators. A separate recovery job resumes known checkouts and discovers lost creation responses in bounded 20-session pages with a durable cursor and fixed creation window. Attempts have a durable uncertainty marker and serialize per checkout; a reloaded purchase resumes its existing reservation. Unattempted intents expire after the creation deadline. If an attempted request has no discoverable result, its reservation remains held and a failed job requests provider investigation. Absence from a list is not proof that charging failed.

The Admin finance workspace shows reconciled provider transactions, payouts, disputes, issues and uncertain checkouts. Resolution requires recent MFA, a reason and authoritative provider evidence. A won dispute restores access only after a verified current merchant-win outcome with no refunds or other adverse disputes and the remaining entitlement checks. Administrative acknowledgement records review and does not claim to adjudicate a bank dispute. [Finance design](finance.md) explains the independent records, refund authority, reconciliation and acceptance boundaries.

Primary references: [Stripe versioning](https://docs.stripe.com/api/versioning), [direct charges](https://docs.stripe.com/connect/direct-charges), [webhooks](https://docs.stripe.com/webhooks), [idempotency retention](https://docs.stripe.com/api/idempotent_requests), [session discovery](https://docs.stripe.com/api/checkout/sessions/list), [official OpenAPI specification](https://github.com/stripe/openapi/blob/master/openapi/spec3.json), and [restricted businesses](https://stripe.com/legal/restricted-businesses). The exact October 7 schema was checked during implementation; the upstream main branch can change.

## Sumsub identity and age

Configure an applicant level with identity-document verification, selfie/liveness and the intended age policy. Use `SUMSUB_MODE=test` for isolated acceptance and `live` for production, with the matching token/account environment. Set `SUMSUB_CLIENT_ID` to the provider's actual client identifier and `SUMSUB_LEVEL` to that level. Mount the app token, API secret, and independent webhook secret. Set the webhook URL to `/api/webhooks/sumsub` and select `HMAC_SHA256_HEX`. API access needs hosted-link generation and applicant/verification-step reads. Do not use a manual webhook test to approve a creator.

The server signs API requests and creates a hosted WebSDK link. A verified callback queues a current-state read under a per-creator database lock. Approval requires matching creator/client/level, completed GREEN overall review, approved ID and selfie steps, and age 18+ calculated from the matching approved document's birth date. User-entered or fixed-profile dates do not override document evidence. Documents, raw birth dates, and webhook payloads are not retained. The database stores provider subject ID, status, timestamps, and a minimal audit event. A provider reversal removes local creator approval. Identity status is refreshed periodically; local moderator approval still remains a separate required action.

Primary references: [hosted WebSDK links](https://docs.sumsub.com/reference/generate-websdk-external-link), [webhook authentication](https://docs.sumsub.com/docs/webhook-manager), [applicant webhooks](https://docs.sumsub.com/docs/user-verification-webhooks), [applicant data](https://docs.sumsub.com/reference/get-applicant-data), and [verification-step results](https://docs.sumsub.com/reference/get-status-of-verification-steps).

## Private media and scanner

The [AWS media template and guide](aws-media.md) now provide locally validated bucket, encryption, workload/replication IAM, audit, retained-replica and alarm configuration. It still requires account deployment, permission tests, and recovery acceptance.

Provision a general-purpose S3 bucket with Block Public Access, bucket-owner-enforced ownership, encryption, versioning, TLS-only policy, access/data-event logging, and a reviewed retention policy. The Rust SDK uses workload credentials and an explicit AWS regional endpoint; custom endpoint overrides are refused. The workload needs bucket inspection and only GetObject, PutObject, and DeleteObject within `S3_PREFIX`, plus scoped KMS permissions if selected. Every request includes the expected 12-digit account owner. The application writes AES256 encryption by default or SSE-KMS with `S3_KMS_KEY_ID`; it never sets a public ACL. S3 storage, requests, transfer, logging, version retention, and KMS incur account charges.

Use an external `MFA_ENCRYPTION_KEY_FILE` containing exactly 32 random **binary** bytes for all processes sharing the database. It encrypts MFA and queued mail; it is separate from S3 server-side encryption. Preserve it through rotation and recovery. Startup verifies existing authenticated ciphertext. The database binds media to its bucket/owner/region/prefix and providers to their environment/account identity, refusing silent switches after data exists. Migrating existing local media to S3 requires a separately reviewed copy/verification procedure; changing environment variables is insufficient.

ClamAV's plaintext protocol is accepted only on loopback, so a deployed scanner must share the application's network namespace. Set scanner timezone UTC. Every upload checks the signature-database date (maximum 48 hours old, at most five minutes into the future), then streams bounded bytes with INSTREAM before decoding/transcoding. Infection rejects the upload; unavailable, stale, or malformed scanner responses leave it held. Application authorization remains in front of all full media, previews, ranges, and captions. Raw uploads have durable ownership before storage writes; workers recover missing processing jobs and retry original-object cleanup.

The local backup commands reject S3/external-key deployments. The [AWS runtime](aws-runtime.md) supplies signed consistent checkpoints, isolated versioned-media/RDS restores and coordinated key rotation. Rehearse them in the target account. Resumable uploads, adaptive HLS and MP4 fallback are implemented. CloudFront disables caching for private app/media responses; every playlist, segment, caption and range remains authorized by the API.

A real local smoke test used official ClamAV 1.5.4 (`clamav/clamav:1.5.4-debian13-slim@sha256:9bb8712a50f0e75166e936c452cd82dd5e5be0b85586598930b5bbb84a99a578`). The app rejected its initially stale database; after loading signature version 28146 dated October 7, it accepted clean input and rejected the harmless EICAR test string. Reproduce with `MEDIA_SCANNER=clamav CLAMAV_ADDRESS=127.0.0.1:3310 cargo run --locked -p myfans-api --example verify_scanner`. The release scanner is now built from pinned ClamAV source on Alpine, with a patched Cargo lock, non-root/read-only operation, capability/resource limits and a separate image gate. See [current scanner evidence](container-findings.md); the historical Debian smoke is not the selected release image.

Primary references: [S3 security practices](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html), [AWS Rust SDK](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/welcome.html), and [ClamAV scanning](https://docs.clamav.net/manual/Usage/Scanning.html).

## Diagnostics and acceptance

After owner-run migrations and runtime-role grants, run `APP_RUN_MIGRATIONS=false myfans-api doctor` with the same mounted configuration as the app. It prints non-secret configuration/probe results and exits unsuccessfully for incomplete provider setup, storage/scanner failure, missing SMTP, or failed jobs. It does not send email, accept payments, publish the app, or certify provider acceptance. It reports the actual runtime mode separately from provider acceptance; `provider_acceptance_completed` remains false because local diagnostics cannot prove account acceptance.

Local tests use protocol fixtures for Stripe, Sumsub and S3. Actual account acceptance still needs hosted onboarding, redirect paths, payment authentication, renewal/failure, duplicate/reordered callbacks, refunds/disputes, bank payout and tax reconciliation, identity rejection/revocation, bucket IAM/KMS denials, mailbox delivery, and coordinated recovery evidence. Record failures and their resolution before activation; [production-readiness.md](production-readiness.md) records the account activation and acceptance requirements.
